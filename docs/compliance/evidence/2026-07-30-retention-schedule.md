## 1. Schedule

| 1 | Raw conversation content (`session_events`) | **30-day policy clock from `summary_generated_at`; healthy-path deletion normally about 30–31 days, not a fixed maximum.** The purge runs daily with a 100-record dispatch cap and must regenerate the summary-only Voyage embedding before deletion. Summary/recap gaps, sustained over-cap volume, or embedding-provider failure defer deletion; null timestamps are remediated by reconciliation through day 37, then requeued and escalated by the purge detector, and over-cap eligible volume emits an alert. ## 2. Deletion-propagation evidence

**Status: tracked engineering item, evidence pending — no test run has been executed.**

The July 26 draft's §6 lays out a 15-item proposed test plan covering: whole-account deletion happy path, person-scoped consent-withdrawal deletion, the transcript-purge cron, the delayed-purge path, bearer-token consent withdrawal, the archive-cleanup (COPPA) path, scheduled TTL crons, subject delete, export/delete parity, a partial-external-failure dead-letter drill, a PITR restore-replay drill, an `email_suppressions` negative check, KV cache invalidation, a Sentry-scrub regression check, and a provider-copy verification (blocked on Actions 7–9).

None of these 15 items has been executed as of this draft. This is the concrete gap behind the DPO's "deletion-propagation test evidence" ask in Action 6 — the mechanism-level *design* is code-verified (§1 above cites live cron code and transaction logic for the categories that are actually built), but there is no recorded test run proving that a real account deletion actually reaches embeddings and provider-side copies as designed. Recommend this become a tracked engineering item (new WI) with the 15-item plan as its acceptance criteria, run against a non-production branch, before this schedule can be represented to the DPO as verified rather than designed.
