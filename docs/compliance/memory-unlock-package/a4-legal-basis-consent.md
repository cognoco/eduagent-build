## Current position

**The purposes and their designated bases are documented and internally agreed; the consent *evidence* mechanism for those purposes is not yet adequate, and this document says so plainly.** The purpose-lane model agreed with management on 2026-07-30 (`docs/compliance/evidence/2026-07-30-purpose-basis-recipient-retention-matrix.md:44-50`) designates **Art 6(1)(a) consent** as the basis for both parked lanes: **P3 — personalization memory** (the "knows-me" persistent memory: durable facts, session summaries used for continuity, semantic recall) and **P4 — inferred profiling and adaptation** (LLM-derived learning style, strengths, struggles, communication notes, inferred interests). Consent is proposed precisely because the service is deliverable without these lanes, so refusal carries no detriment and the choice is genuine — the condition that makes consent freely given for a child (matrix `:59-62`, `:142`). The neighbouring lanes P1/P2/P2b (mentoring delivery, learning record, declared preferences) rest on Art 6(1)(b) contract; the P2/P3 boundary — record of *what was taught* (contract) versus record of *the learner as a person* (consent) — is the load-bearing distinction and is put to the DPO for testing at matrix `:52-66`. The existing top-level documents are directionally consistent with this (consent for "the minor's learning/profiling": `docs/compliance/dpia.md:61`; ROPA rows 7 and 9 name "Consent" as the basis for persistent learning memory and embeddings: `docs/compliance/ropa.md:54,56`) but are imprecise in ways itemised in the Gaps section.

**A distinct consent moment, a distinct off-switch, and fail-closed enforcement of the memory consent all exist in the shipped code — but the consent leaves no evidence record.** Two separate consent mechanisms coexist (`docs/compliance/evidence/2026-07-30-consent-log-spec.md` §1): **Mechanism A**, the regulatory consent log (`consent_request` / `consent_grant` / `consent_receipt` tables), covers exactly two purposes — `platform_use` and `llm_disclosure` (`packages/schemas/src/consent.ts:20`) — with versioning, at-grant snapshots, guardian-vs-self encoding in `lawful_basis`, stamped withdrawal, and receipts that survive erasure. **Mechanism B**, the memory consent, is a single mutable column — `learning_profiles.memory_consent_status`, enum `pending | granted | declined`, default `'pending'` (`packages/database/src/schema/learning-profiles.ts:36-40`) — written by exactly two production writers (`grantMemoryConsent`, `apps/api/src/services/learner-profile.ts:2192-2215`; `toggleMemoryCollection`, `:2130-2159`), with no grant timestamp, no policy version, no grantor identity, no history, and no survival past erasure. Every memory write and injection path refuses unless the status is `'granted'` (enforcement inventory at consent-log-spec §3.3), so the control works; what is missing is the Art 7(1) *record*. One of the two writers is an **implicit grant path**: switching the memory-collection toggle on silently sets `memory_consent_status = 'granted'` as a side effect (`learner-profile.ts:2143-2145`) and stamps `consent_prompt_dismissed_at` so the explicit consent prompt is never shown afterwards (`:2153`).

**The interim "disabled" condition is currently held by defaults and by the absence of users, not by a switch.** There is no server-side kill switch for persistent memory: the only memory-related config flags select which storage generation is *read*, not whether memory is processed (`apps/api/src/config.ts:151-153`, per the flag comments; finding restated at matrix `:76-87` and `docs/compliance/evidence/2026-08-04-wi-2919-memory-claim-copy-audit.md:56-70`). The condition holds because (a) the product is pre-launch with zero users and (b) `memory_consent_status` defaults to `'pending'` and every processing site fail-closes on it. The operator ruled provisionally on 2026-08-05 that the per-profile fail-closed consent gating as built satisfies the interim condition and that no global kill switch is required; that ruling is **pending DPO ratification (OPQ-169)** (`2026-08-04-wi-2919-memory-claim-copy-audit.md:27-32`). The remediation that moves memory consent into the evidence log and removes the implicit grant path is scoped and operator-ruled but **not implemented** (**PLANNED, WI-2928** — see Gaps §1).

## Consent and withdrawal design

The design has two layers. The **regulatory layer** (Mechanism A) governs platform use and LLM disclosure and carries the Art 8 parental-consent workflow; the **memory layer** (Mechanism B) is the P3/P4 opt-in. Both are described as built, with EXISTS / PLANNED clearly separated.

### 1. Who consents (Art 8 posture)

- **EEA launch perimeter is threshold-13 countries** (Route 1 of the screen-based allowlist, `docs/compliance/2026-07-26-launch-perimeter-ruling-screen-based-allowlist.md`; country register `docs/compliance/2026-07-23-13-plus-eea-launch-country-ruling.md`; the per-country `article8Threshold` is modelled as an integer 13–16 in `packages/schemas/src/country-policy.ts:145`). The documented intent for the consented lanes: *"Teen consents where self-consent applies; Guardian where it does not"* (`ropa.md:39`); the EDPB fill states the same banded model (`edpb_dpia_filled_2026_v1.md:186`).
- **Regulatory layer, as built:** the shipped consent machine requires guardian consent for learners aged 16 and under (calendar-conservative year-only handling; 17+ self-stand) — `checkConsentRequired`, `apps/api/src/services/consent.ts:222-247`, and its date-precise twin `checkConsentRequiredFromDate` `:140-167`, both fail-closed on unknown age. Adults (18+, `admin` membership) self-consent under basis `art6_1_a` at signup (`recordAdultSelfConsentV2`, `apps/api/src/services/identity-v2/consent-v2.ts:314-351`) or via the authenticated acceptance endpoint (`acceptAdultSelfConsentV2`, `:743-839`).
- **Memory layer, as built:** for a **13–17 learner on a parent account** (non-owner profile), memory consent is guardian-granted: the self routes are gated by `assertCanManageOwnConsent`, which denies minor non-owners (*"Minor non-owner profiles cannot self-grant or self-revoke memory consent — the parent's grant … must not be overridden"*, `apps/api/src/routes/learner-profile.ts:304-307`; gate logic at `apps/api/src/services/family-access.ts:146-176` — owner allowed, adult non-owner allowed, minor non-owner denied). The guardian grants or declines through `POST /learner-profile/:profileId/consent` (`routes/learner-profile.ts:320-338`), surfaced on the guardian-voiced child memory screen (`apps/mobile/src/app/(app)/child/[profileId]/mentor-memory.tsx:396-433`; copy: "Help the mentor learn about {{name}}" / "Yes, enable" — `docs/compliance/evidence/2026-07-30-consent-screen-inventory.md:202-207`).
- **Caveat, as built:** `assertCanManageOwnConsent` permits the **account owner regardless of age** (`family-access.ts:162-165`). A 13–17 self-registered owner can therefore operate the memory consent themselves. Nothing in the record distinguishes a guardian grant from a learner grant — both paths write the same column with no actor field (P3-G3, consent-log-spec `:391`; screen inventory `:213-223`). Whether teen self-consent for P3/P4 in threshold-13 countries is the *intended* design is exactly the Art 8 question this package puts to the DPO; today it is the emergent behaviour, and it is unevidenced either way. **PLANNED, WI-2928** records grantor identity in `audit_fact`, closing the evidencing half.

### 2. The consent moment — screens and capture

**EXISTS — memory (Mechanism B):**
- A distinct opt-in prompt component with explicit Grant ("Yes, enable") and Decline ("Not now") actions: `apps/mobile/src/components/memory-consent-prompt.tsx` (testIDs `memory-consent-grant` / `memory-consent-decline`), rendered on the learner's own memory screen when status is `'pending'` and the viewer is the owner (`apps/mobile/src/app/(app)/mentor-memory.tsx:431-434`) and on the guardian's child screen when the child's status is `'pending'` (`child/[profileId]/mentor-memory.tsx:396-433`). Full shipped copy inventoried at screen-inventory §5.1.
- The prompt calls `POST /learner-profile/consent` (self) or `POST /learner-profile/:profileId/consent` (guardian), which run `grantMemoryConsent` — a single `UPDATE` of `learning_profiles` setting `memory_consent_status` and the three enable booleans (`learner-profile.ts:2192-2215`). **No `consent_grant` row, no version, no grantor, no receipt is written** (verified: the function touches only `learning_profiles`).
- A second, **implicit** grant path: the "Learn about child" collection switch (`child/[profileId]/mentor-memory.tsx:446-456`) calls `PATCH /learner-profile[/:profileId]/collection` → `toggleMemoryCollection`, which sets `memory_consent_status = 'granted'` as a side effect of enabling collection (`learner-profile.ts:2143-2145`) and suppresses the future consent prompt via `consent_prompt_dismissed_at` (`:2153`). Toggling **off** does not revoke — the prior status is preserved (`:2145`). Finding C-3 / gap P3-G5 (consent-log-spec `:286-290`, `:393`). **PLANNED, WI-2928** removes this implicit grant path.
- Placement: the memory control lives on the "Mentor memory" screen under the More tab's **"Your learning"** section (`apps/mobile/src/app/(app)/more/index.tsx:135-141`), **not** on the app's own "Privacy & data" screen — `more/privacy.tsx` contains no memory or profiling control at all (verified; screen contents at `apps/mobile/src/app/(app)/more/privacy.tsx:97-155`; finding at screen-inventory §4.1). **PLANNED, WI-2928** surfaces the memory control on the Privacy & data screen.
- Enforcement behind the moment is fail-closed at every site: profiling write refused unless `memoryConsentStatus === 'granted'` and collection enabled (`learner-profile.ts` applyAnalysis gate, with in-transaction re-check; post-session write `apps/api/src/inngest/functions/session-completed.ts:1725-1748`); injection refused without granted status (`apps/api/src/services/memory/memory-facts.ts:168-173`; `apps/api/src/services/curated-memory.ts:199`); the injection toggle itself refuses to enable without consent (`[F-PV-09]`, `learner-profile.ts:2176-2178`); embedding backfill filters to granted, non-archived profiles (`apps/api/src/inngest/functions/memory-facts-embed-backfill.ts:129-140`).

**EXISTS — regulatory (Mechanism A), summarised because memory consent for minors sits on top of it:**
- Parental consent request/approve workflow: in-app request screen capturing the parent's email (`apps/mobile/src/app/consent.tsx`), email token (7-day expiry), approval writing one `consent_grant` per purpose with `policy_version`, at-grant age/jurisdiction snapshots, and a back-linked request row (`processConsentResponseV2`, `apps/api/src/services/identity-v2/consent-v2.ts:1160-1283`); parent-created child grant (`createDirectConsentGrant`, `:240-283`); adult self-consent as above. Resend/recipient-change abuse caps (WI-374) at `:869-1014`.
- **Policy versioning:** every production grant writer stamps the server's `CONSENT_POLICY_VERSION` into the first-class `consent_grant.policy_version` column, which no withdrawal path writes — the grant-time wording is structurally immutable (**landed 2026-08-05**: WI-2929, commit `ab71a5a8d` / PR #2974, migration `apps/api/drizzle/0168_wi2929_consent_evidence_durability.sql`; column at `packages/database/src/schema/identity.ts:544`). This closed prior finding C-2 / gap P3-G4, and it is the prerequisite that lets a future memory purpose enter the log without inheriting the defect (consent-log-spec `:392`, `:405-408`).
- Known weakness on this layer, relevant context for A4: the only explicit adult consent screen, `AdultSelfConsentGate`, is **not mounted anywhere in the shipped app** (verified: no renderer of the component and no reader of the `needsAdultConsent` signal in `apps/mobile/src`; the component's own docblock assigns mounting to WI-2411 — `apps/mobile/src/app/(app)/_components/AdultSelfConsentGate.tsx:31`). Combined with the enforcement gate being fail-open for a user with no grant row, this is tracked as launch-blocking finding C-4 / CL-O8 (consent-log-spec `:330-338`, `:434`). No client screen displays or transmits a policy version; versioning is server-side only (verified: no `CONSENT_POLICY_VERSION` reference in `apps/mobile/src`).

**PLANNED (not implemented — do not rely on):**
- **WI-2928 — memory-consent hardening.** Operator-ruled 2026-07-31 with full scope: record memory consent as a `consent_grant` **purpose** with version and grantor in `audit_fact`; surface the control on the Privacy & data screen; remove the implicit grant path. Not implemented: Stage=Captured, unclaimed, and the repository contains no WI-2928 reference in code, docs, or git history (verified by repo-wide grep and `git log --grep`). Its technical shape matches the recommendation already recorded at consent-log-spec §6.1 (add a `personalization_memory` purpose; demote `memory_consent_status` to a derived enforcement cache).
- **Memory-specific transparency copy** (choice disclosure, child-facing memory notice) is drafted but deliberately not shipped until unlock (`docs/compliance/evidence/2026-07-30-child-notice-memory-section-draft.md:7`); today's notices describe memory as automatic rather than as a choice — transparency finding S-5, owned by element A13 (screen-inventory §6).

### 3. Withdrawal design and its consequences

**EXISTS — withdrawal of memory consent (Mechanism B):**
- The same guardian/self surfaces accept `'declined'` (`grantMemoryConsentSchema`; `grantMemoryConsent` sets status `declined` and all three enable booleans false — `learner-profile.ts:2201-2214`). Processing stops at every enforcement site listed above. **Consequence for data:** stored memory is *not* deleted by declining; deletion is a separate, always-available user action — "Clear all mentor memory" → `deleteAllMemory`, which hard-deletes `memory_facts` and the `learning_profiles` row; a fresh row recreates at `'pending'` so collection and injection stay off until re-granted (`learner-profile.ts:2224-2237`; UI dialog copy "This removes everything the mentor has remembered about you and turns memory off…" — screen-inventory §5.2). The erasure routes deliberately remain available even when the child's regulatory consent is withdrawn (`routes/learner-profile.ts:196-197`).
- **Consequence for evidence:** withdrawal leaves **no record that consent was ever granted** — the column is overwritten; there is no grant timestamp, no history, no receipt (consent-log-spec §3.4: *"After a withdrawal, the controller cannot demonstrate that P3 consent was ever validly obtained"*). `[GAP: no demonstrable Art 7(1)/5(2) trail for memory consent before or after withdrawal — remedied by PLANNED WI-2928.]`

**EXISTS — withdrawal of the regulatory consent (Mechanism A), which memory processing also hangs on:**
- **Guardian in-app withdrawal:** "Withdraw consent" on the child detail screen with an explicit consequence dialog (*"{{childName}}'s account and learning data will be deleted after a 7-day grace period. (For under-13 accounts, deletion is immediate at grace expiry…)"* — `apps/mobile/src/app/(app)/child/[profileId]/index.tsx:596-615,733-751`) → `revokeConsentV2`, guardian-edge-authorised (`consent-v2.ts:1473-1488`).
- **Email-parent bearer-token withdrawal (P0):** the consenting parent without an app account withdraws by possession of the signed link (`withdrawConsentByToken`, `consent-v2.ts:1505-1532`). Threat posture ruled 2026-07-17 (OPQ-114), documented at `docs/compliance/2026-07-17-consent-withdrawal-bearer-token-threat-posture.md`; the token is withdraw-only (restore requires an authenticated guardian session — posture doc header amendment), and the mitigate-before-launch item (server-side supersession of links) is implemented as the `withdrawal_token_id` exact-match discipline (WI-2347/WI-2434 — `consent-v2.ts:1542-1554`, minting at `:1186`).
- **Mechanics:** withdrawal stamps `withdrawn_at` (+ `prior_value`, withdrawal-provenance `audit_fact`) on the live grant set — the one sanctioned in-row transition — mirrors the withdrawal onto the durable `consent_receipt`, and marks the child's unread nudges read (`stampWithdrawal`, `consent-v2.ts:1556-1627`). The grant-time `policy_version` survives by construction (WI-2929, `:1593-1598`). Adults withdraw per-purpose via `withdrawAdultSelfConsentV2` (`:364-461`); however **no mobile UI calls the self-withdraw endpoint** — the schema exists (`packages/schemas/src/consent.ts:162`) but the only in-app adult paths are the memory opt-out and account deletion (verified across `apps/mobile/src`). `[GAP: no in-app adult self-consent withdrawal surface, while the privacy policy's rights section promises in-app withdrawal — see Gaps §7.]`
- **Consequences for data:** immediate access cut-off via `ConsentWithdrawnGate` (`apps/mobile/src/app/(app)/_components/ConsentWithdrawnGate.tsx`, mounted at `_layout.tsx:976`) and server-side denial of LLM dispatch on a withdrawn purpose (`assertLlmConsent` before every LLM-dispatching learner-profile route, `routes/learner-profile.ts:350-353,370-375`, WI-2396). Then the scheduled pipeline (`apps/api/src/inngest/functions/consent-revocation.ts`): day-6 warning push → 7-day grace with in-app restore ("Cancel deletion" / "Reverse" banners; restore appends a new grant and un-archives, `appendRestoreGrant` area `consent-v2.ts:1641-1741`; grace constant `RESTORE_CONSENT_GRACE_PERIOD_MS`, `apps/api/src/services/consent.ts:108`) → at grace end, **hard delete** where age ≤ 13, age unknown, or the owner preference is "never archive", otherwise **30-day archive then hard delete** (`consent-revocation.ts:267-270`; `archive-cleanup.ts` 30-day window; owner preference captured on the Privacy & data screen, `more/privacy.tsx:98-128`). Hard delete erases the person row; `learning_profiles` and `memory_facts` are erased via their `ON DELETE CASCADE` foreign keys (`learning-profiles.ts:21-24`, `memory-facts.ts:22-24`) — the deletion service does not name the memory tables directly. The DPIA records the re-home-then-delete pattern preserving the consent receipt and deletion audit while erasing the person and learning data (`dpia.md:71`).
- **Honest limitation, stated for the DPO:** a regulatory withdrawal does **not** clear the memory flag. `memory_consent_status` remains `'granted'` after `revokeConsentV2`; the codebase compensates with an explicit second gate at each memory write site (*"revokeConsent sets GDPR status to WITHDRAWN without clearing memoryConsentStatus, so the existing memory gate alone is insufficient"* — `learner-profile.ts:1649-1652`; same rationale at `session-completed.ts:1732-1738`). Both layers are checked, so processing does stop; but the stopped state is enforced by a conjunction of runtime checks rather than by consistent stored state, and during a 30-day archive window the memory rows persist untouched with the flag still reading `granted` (only `person.archived_at` is stamped; `archivePersonOnRevocationV2`, `consent-v2.ts:2218-2250`). The embedding backfill additionally filters on `archived_at` (`memory-facts-embed-backfill.ts:137`); the write-path gates do not consult it and rely on the consent-grant state instead.

**PLANNED:** WI-2928 gives memory consent its own purpose row in the log, making memory withdrawal a first-class, stamped, evidenced event with the same mechanics as the regulatory purposes.

## Gaps and proposed remediation

Numbered for the DPO. Severity labels follow the repo's own consent-log spec §6 where applicable.

1. **Memory consent is not in the consent log** (P3-G1, Blocking). A mutable column with no timestamp, version, history, or post-erasure survival cannot demonstrate consent under Art 7(1)/5(2). — *Remedy:* **PLANNED, WI-2928** (operator-ruled 2026-07-31; Stage=Captured, unclaimed; no implementation in the repo): record memory consent as a `consent_grant` purpose with version and grantor in `audit_fact`. Prerequisite WI-2929 (evidence durability) **landed 2026-08-05** (commit `ab71a5a8d`, PR #2974), so the new purpose inherits the structural version guarantee.
2. **No `personalization_memory` / profiling purpose exists in `CONSENT_PURPOSES`** (P3-G2, Blocking; `packages/schemas/src/consent.ts:20`). P3/P4 consent has nowhere to live in the evidence log. — *Remedy:* within WI-2928, per consent-log-spec §6.1.
3. **No guardian-vs-learner distinction is recorded for memory consent** (P3-G3, Blocking for minors). Both routes write the same column with no actor; additionally, an account owner of any age passes the gate (`family-access.ts:162-165`), so a 13–17 owner can self-grant with no record of who consented. — *Remedy:* grantor in `audit_fact` (WI-2928); the *policy* question — whether teen self-consent for P3/P4 is intended in threshold-13 countries — is put to the DPO in §"Who consents" above and should be ruled before unlock.
4. **The implicit grant path** (Finding C-3 / P3-G5, High): enabling the collection toggle silently writes `granted` and permanently dismisses the consent prompt (`learner-profile.ts:2143-2145,2153`), on a switch whose surface carries no consent wording. Doubtfully an affirmative, informed act under Art 4(11). — *Remedy:* **PLANNED, WI-2928** removes the implicit path (toggle becomes inert without a prior explicit grant).
5. **The memory control is absent from the app's own "Privacy & data" screen** — it lives under "Your learning" (`more/index.tsx:135-141`; `more/privacy.tsx` has no memory control). — *Remedy:* **PLANNED, WI-2928** surfaces it on Privacy & data.
