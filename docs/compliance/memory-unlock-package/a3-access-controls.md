## Current position

**Age assurance is the strongest of the three legs.** The product enforces a server-side 13+ floor on exact, self-declared date of birth at the API trust boundary: the Zod schema rejects any birth year that could belong to a person under 13, and — since WI-3019 (server-side full-birth-date requirement, merged to `main` 2026-08 via PR #2972, commit `0308e7965`) — a payload in the ambiguous floor year must carry the full month and day, closing the previously documented gap where a year-only API call could register a not-yet-13 learner. Exact-date banding (`computeAgeBracketFromDate`) is the canonical gating function for safety-adjacent decisions. Age remains **self-declared and uncorroborated**; the proportionality argument for that posture is set out in the existing evidence document `docs/compliance/evidence/2026-07-30-age-assurance-design.md` and is not repeated here. A store-provided age-signal corroboration layer (WI-1116) is planned, not implemented.

**Residence determination is the weakest leg.** The purpose-built ISO-3166 country-policy resolver (`resolveJurisdiction`, built under WI-2690) exists, is fail-closed, and — an advance on the 2026-07-30 evidence draft — now has production callers in the guardian-attachment and family-join flows. However, it is still **not invoked at signup, onboarding, or session start**, and the family-join callers sit behind a feature flag that defaults off. The only residence signal collected at profile creation is the legacy, optional, three-bucket `location` field (EU/US/OTHER), which the shipped mobile client never populates; every mobile signup therefore stores the default jurisdiction `ROW`. In consequence, the launch-perimeter ruling's stated control model ("store distribution config + in-app residence gating") is not yet implemented as a working in-app technical control, and store-level geographic restriction cannot be verified from this repository.

**Memory access is controlled by per-profile consent, not by any global or launch-state gate.** The design is fail-closed at the profile level: memory consent defaults to `pending` and collection defaults to `false` on every learning-profile row, both the transcript-analysis write path and every prompt-injection path check consent before acting, and consent management is restricted to the account owner, verified adults (18+), or the parent through owner-gated child routes — a minor on a parent account cannot self-grant. What does **not** exist is a global kill-switch implementing the DPO's interim "persistent memory + profiling stay disabled" condition: the environment flag `MEMORY_FACTS_READ_ENABLED` is a storage-backend selector, not a feature gate, and the consent prompt renders to every new account owner. This state was audited in full on 2026-08-04 (WI-2919) and dispositioned by a **provisional operator ruling of 2026-08-05** — that the per-profile fail-closed consent gating satisfies the interim condition — which is **pending DPO ratification as OPQ-169** and is exactly the question this evidence package puts to the DPO. The interim condition's "no public processing" element is currently met by the pre-launch zero-user state, not by a technical gate.

## Narrative

### 1. Residence determination

**Policy layer.** The launch perimeter is a screen-based allowlist ruled by management on 2026-07-26 and revised per the DPO's M3 wording of 2026-07-30: EEA countries with a verified Article 8 self-consent threshold of 13 enter via Route 1 under the maintained country register (`docs/compliance/2026-07-23-13-plus-eea-launch-country-ruling.md`); non-EEA jurisdictions enter only through a dated admission screen (Route 2). The United States is **provisionally screened, not finally admitted** (`docs/compliance/2026-07-26-us-launch-screen-record.md`; conditions include WI-1116, launch-day rechecks, and signed management risk acceptance). UK, Poland and other higher-threshold EEA states, and Switzerland are out at launch (`docs/compliance/2026-07-26-launch-perimeter-ruling-screen-based-allowlist.md`). The 07-23 ruling requires the governing residence input to be **habitual residence** — not nationality, UI language, IP address, or app-store country — and requires unknown or conflicting residence to fail closed.

**What the running application does today.** Two residence mechanisms exist in the codebase and they are not the same one:

1. *The collected signal.* Profile creation accepts an **optional**, self-declared, three-bucket `location` field — `'EU' | 'US' | 'OTHER'` (`packages/schemas/src/profiles.ts:6`, `:88`). The shipped mobile client contains **no UI that collects it**: a repository search of `apps/mobile/src` finds `location` only in test fixtures (always `null`) and unrelated code. An absent value is mapped to the default jurisdiction `'ROW'` at graph creation (`apps/api/src/services/identity-v2/identity-graph.ts:70-84`) and stored on `person.residence_jurisdiction` (`packages/database/src/schema/identity.ts:86`). In practice, therefore, **every profile created through the shipped app carries the default residence bucket, and no user-facing flow asserts habitual residence.** The three-bucket shape also cannot distinguish threshold-13 from higher-threshold EEA countries, so it cannot drive the country register even where it is populated.

2. *The enforcement machinery.* A purpose-built resolver exists (WI-2690): `resolveJurisdiction()` (`apps/api/src/services/identity-v2/country-policy-loader.ts:104`) reads the effective-dated `country_policy_registry` and returns a typed allow/block decision; the schema layer (`packages/schemas/src/country-policy.ts`) defines ISO 3166-1 alpha-2 country codes and a residence-assurance object in which methods such as geo-IP, billing address, storefront country, and device locale may only ever *corroborate* a primary self-report or verified credential. The resolver is fail-closed on unknown, malformed, or unsupported input (design detailed in `docs/compliance/evidence/2026-07-30-residence-determination-design.md` §3). Since that document was written, the resolver has gained production call sites: the guardian-attachment ceremony refuses to proceed unless the resolver returns `launchDecision === 'allowed'` with a guardian-required consent decision (`apps/api/src/services/identity-v2/guardian-attachment.ts:221-236`), and the family-join journey calls it at `family-join-journey.ts:213` and `:603`. The family-join surface, however, is dark: every `/v1/family-join/*` request is 404-gated behind `FAMILY_JOIN_ENABLED`, which defaults to `'false'` (`apps/api/src/config.ts:146`; `apps/api/src/middleware/family-join-gate.ts:52-62`).

3. *The gap between them.* No route, onboarding handler, or session-start path calls `resolveJurisdiction()` for ordinary account creation or product access. The perimeter ruling's control model — "store distribution config + in-app residence gating" — is therefore only half-verifiable from this repository, and the verifiable half is **absent**: in-app residence gating of general access does not exist today. Store-level geographic availability is configured in App Store Connect / Google Play Console, outside this repository; `apps/mobile/eas.json` carries no country restriction (read recorded in `docs/compliance/evidence/2026-07-30-residence-determination-design.md` §4). See Gaps 1 and 2.

**Honest summary for the DPO:** the country register and admission screens are complete policy artifacts; the enforcement code exists and is fail-closed but is wired only into two guardian/family flows (one of them flag-disabled), not into signup or general access. Until the wiring lands, the launch perimeter is operationally enforceable only at the store-distribution layer, which must be evidenced from the store consoles, not this repository.

### 2. Age assurance

**Collection.** Every profile-creation request must declare a birth year; the shipped mobile client always sends the exact date of birth (year, month, day) derived from a date picker (`apps/mobile/src/app/create-profile.tsx:347-349`). `birthMonth`/`birthDay` are create-only and immutable through the update path (`packages/schemas/src/profiles.ts:76-80` comment).

**Enforcement of the 13+ floor.** Two server-side layers, both at or behind the API trust boundary:

- `birthYearSchema` rejects any `birthYear` later than `currentYear − 13`, using a `≤` threshold that deliberately compensates for month-level overestimation so a boundary-year December birth cannot slip through as 13 (`packages/schemas/src/profiles.ts:39-57`).
- **WI-3019** (server-side full-birth-date requirement — merged to `main`, PR #2972, commit `0308e7965`; membership in `origin/main` verified 2026-08-07): where a year-only payload would be ambiguous against the floor (birth year at the cap), the schema now **requires** `birthMonth`/`birthDay` (`packages/schemas/src/profiles.ts:98-141`), and both creation writers additionally enforce the floor through the conservative service-side check `isBelowMinimumAgeAtCreation` (`apps/api/src/services/consent.ts`, per the WI-3019 record in `docs/compliance/privacy-publication-manifest.md` §4). This closes the under-13 registration gap that the 2026-08-01 reconciliation had flagged as a publication blocker: a direct API call can no longer register a not-yet-13 user by omitting month and day.

**Banding for gating decisions.** `computeAgeBracketFromDate()` (`packages/schemas/src/age.ts:78-96`) is the canonical exact-date banding function for feature gating and safety-adjacent decisions (`AGENTS.md` § Profile Shapes), returning `child` (<13, unreachable through any current API per the schema floor), `adolescent` (13–17), `adult` (18+). It is used, inter alia, in the guardian-attachment admission checks (`apps/api/src/services/identity-v2/guardian-attachment.ts:185-219`). The stricter fail-closed variant `isUnambiguouslyAdult()` (`age.ts:135-141`) exists for PII-egress gates and treats the 18-boundary year as still-minor.

**Assurance level.** The model is **self-declaration of an exact date of birth, uncorroborated** — no document, credential, payment-instrument, or store signal verifies the declared date at signup. The proportionality case for this posture at current scale and product shape (no social features, no under-13 marketing, 13+ floor at the Article 8 maximum, full 13–17 protections applied regardless of declared position within the band) is made in `docs/compliance/evidence/2026-07-30-age-assurance-design.md` §4 and responds directly to the DPO's Article 8 condition of 2026-07-30 that age assurance be "proportionate to risk." A store-level age-category/parental-consent signal (Apple developer APIs) is a **planned strengthening layer only** — tracked as WI-1116, an open US-screen admission condition, not shipped (perimeter ruling; age-assurance design §5).

**Relevance to memory.** Memory access is not gated on age bracket directly (see §3); age enters the memory picture through (i) the 13+ product floor, which bounds the youngest possible memory subject, and (ii) the adult check inside the consent-management guard (§3, Gap 5).

### 3. Controls governing which users may access the memory function

**Default state — fail-closed per profile.** Every `learning_profiles` row is created with `memory_consent_status = 'pending'` and `memory_collection_enabled = false` (`packages/database/src/schema/learning-profiles.ts:36-46`). `memory_enabled` and `memory_injection_enabled` default `true` (`:35`, `:47-49`) but are inert without granted consent, because every consuming path re-checks consent:

- **Collection (write) path.** The post-session transcript analysis that builds the learner profile runs only when `memoryConsentStatus === 'granted'` AND `memoryCollectionEnabled !== false` (`apps/api/src/inngest/functions/session-completed.ts:1722-1730`), and — before the transcript is transmitted to any LLM provider — additionally verifies that GDPR consent has not been withdrawn via `isLlmExchangeConsentAllowed()` (`:1742-1748`, WI-221/WI-2396: withdrawal blocks the regulated processing act itself, not merely the write).
- **Injection (read-into-prompt) path.** `buildMemoryBlock()` returns an empty block unless consent is granted (`apps/api/src/services/learner-profile.ts:847-853`, F-PV-09); the curated settings view applies the same rule (`apps/api/src/services/curated-memory.ts:196-201`); and the live session prompt-assembly path passes exactly these per-profile fields as its only suppression inputs (`apps/api/src/services/session/session-exchange.ts:3644`; traced in full in `docs/compliance/evidence/2026-08-04-wi-2919-memory-claim-copy-audit.md` §2.3b).
- **Server-side refusal.** Injection cannot be toggled on for a profile whose consent is not granted (`apps/api/src/services/learner-profile.ts:2175-2178`).

**Who may operate the consent and toggles.** Two route families in `apps/api/src/routes/learner-profile.ts`:

- *Self routes* (`POST /learner-profile/consent` `:300-318`; `PATCH /learner-profile/collection` `:202-226`; `PATCH /learner-profile/injection` `:251-275`) are guarded by `assertCanManageOwnConsent` (`apps/api/src/services/family-access.ts:146-186`), which (i) rejects any request without an explicitly selected, verified profile — the auto-synthesized owner identity from a headerless call is refused (Issue 901, `:157-161`); (ii) permits the account owner (`:162-165`); (iii) permits a non-owner only if 18+ (`:179-184`); and (iv) refuses minors on a parent account with the message "Minor profiles on a parent account cannot modify consent or collection settings. Ask your parent or guardian to make this change." Data-collection consent for a child on a parent account is therefore parent-controlled by construction (CR-2026-05-21-010 comments at `routes/learner-profile.ts:206-208`, `:255-257`, `:304-307`).
- *Parent-on-child routes* (`POST /learner-profile/:profileId/consent` `:320-338` and the sibling collection/injection routes) require `assertOwnerAndParentAccess` — an `isOwner` gate plus a parent→child link check against IDOR (`apps/api/src/services/family-access.ts:188-205`) — and `assertChargeNotCredentialed`. Privacy-reducing actions (disabling collection/injection, erasure) deliberately remain available after consent withdrawal (WI-156 comments, e.g. `:236-237`, `:196-197`).
- *Grant paths.* Consent becomes `granted` through `grantMemoryConsent()` (`apps/api/src/services/learner-profile.ts:2192-2215`) or — a second, equivalent-authority path — by enabling collection, which records the grant (`toggleMemoryCollection`, `:2143-2152`). Both are reachable only through the guarded routes above. The in-app consent prompt renders for owners whose consent is pending (`apps/mobile/src/app/(app)/mentor-memory.tsx:434-443`).
- *Erasure.* `deleteAllMemory()` hard-deletes the `memory_facts` rows and the learning-profile row; any later access recreates a fresh row in the `'pending'` fail-closed default (`apps/api/src/services/learner-profile.ts:2217-2237`).

One consequence should be stated plainly for the DPO: a **13–17-year-old who owns their own account** (solo learner, `isOwner = true`) can self-grant memory consent — the owner branch of `assertCanManageOwnConsent` does not age-check (`family-access.ts:162-165`). This is the intended design under the Article 8 threshold-13 position the DPO concurred with on 2026-07-30 (self-consent capacity at 13 in the launch countries), but its lawfulness is **residence-dependent**, and the application does not condition the grant on residence — it relies on the launch perimeter to keep higher-threshold-country minors out. Since the in-app residence gate does not exist yet (§1), this reliance currently rests on store-level distribution alone. See Gap 4.

**The interim "disabled" condition — how memory is actually held off today.** The DPO interim condition states that persistent memory and profiling stay disabled until this package is approved. The repository evidence on *how* that is implemented is the WI-2919 audit (`docs/compliance/evidence/2026-08-04-wi-2919-memory-claim-copy-audit.md`, 2026-08-04, coverage-corrected 2026-08-05), whose findings this section adopts and which must not be overstated:

- **There is no global kill-switch.** `MEMORY_FACTS_READ_ENABLED` (default `'false'`, `apps/api/src/config.ts:148-151`) selects the storage backend (legacy JSONB columns vs. the normalised `memory_facts` table); with it off, reads and prompt injection fall back to the JSONB columns rather than returning empty (audit §2.1, §2.3b). Write paths carry no parked-state gate (§2.2). The memory UI entry point renders unconditionally and the consent prompt is live for every new owner (§2.4).
- **The effective control is the per-profile fail-closed consent gating described above** — memory collection and injection are off for every profile until an authorized person grants consent — combined with the factual pre-launch state: zero users, so no public processing occurs (`action-register-tracker.md`, Interim operating conditions: "Compliant: zero users, pre-launch").
- **Disposition status.** On 2026-08-05 the operator ruled **provisionally** that this per-profile consent gating satisfies the interim parked condition and that no global kill-switch is required, explicitly accepting rework risk. That ruling is **pending DPO ratification (OPQ-169)** and is not represented here as a settled compliance position (audit §0, §7 item 1). This evidence package is the vehicle by which the DPO is asked to either ratify that position or require the genuine park described in audit §7 item 2 (a gate covering read `projection.ts:290`, write `learner-input.ts:233` / `topic-probe-extract.ts:418`, and injection `session-exchange.ts:3617-3643` / `curated-memory.ts:196-200`).

## Gaps and proposed remediation

1. **[GAP: No in-app residence determination or gating at signup — the shipped app never asks for, and never enforces, habitual residence; every mobile signup stores the default `ROW` bucket, and `resolveJurisdiction()` is not called on any general-access path.]** *Remedy:* wire habitual-residence collection (ISO alpha-2 + `residenceAssurance` self-report with corroborating signals per `packages/schemas/src/country-policy.ts`) into onboarding/profile creation and call `resolveJurisdiction()` fail-closed before account activation, per the recommendation already recorded in `docs/compliance/evidence/2026-07-30-residence-determination-design.md` §5. *Tracking:* no Work Item found in the repository for this wiring as of 2026-08-07 — one must be opened; the resolver itself was WI-2690.
