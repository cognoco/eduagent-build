## Current position

**The transparency surfaces largely exist, are live, and are accurate to what the system does.** The persistent-memory feature is fully built: a learner-facing memory screen ("What your mentor knows about you", `apps/mobile/src/app/(app)/mentor-memory.tsx`), a guardian-facing equivalent for managed children (`apps/mobile/src/app/(app)/child/[profileId]/mentor-memory.tsx`), a consent prompt component (`apps/mobile/src/components/memory-consent-prompt.tsx`), and memory-disclosure copy across the app — audited at 67 keys in the three dedicated memory namespaces plus 62 further keys in ten other namespaces, identical across all 7 shipped UI locales (WI-2919 audit §3–§4.1b). The WI-2919 audit's central finding is directly relevant to this package: the DPO interim condition ("persistent memory + profiling stay disabled") has **no implementing gate in code** — memory read, write and prompt-injection paths are live at launch, gated solely by per-profile consent (audit §2, citing `apps/api/src/services/curated-memory.ts:196-200` and `apps/api/src/services/session/session-exchange.ts:3584-3643`). On 2026-08-05 the operator ruled **provisionally** that the interim condition is satisfied by that per-profile fail-closed consent gating; that ruling is pending DPO ratification as OPQ-169 (audit §0). Because memory genuinely operates, the audit found the shipped copy accurate and expressly contraindicated rewording it to session-scoped phrasing (audit §6).

**Inspect / correct / disable / delete are substantially implemented in-app.** The learner's own memory screen shows every remembered category in plain language, allows per-item removal (with suppression so the item is not re-inferred), full clear ("Clear all mentor memory"), a "Use saved notes in lessons" toggle that switches memory injection off without deleting data, correction of interest context, a "Hidden Items" section with restore, and a "Tell Your Mentor" input for user-authored additions — all verified by direct read of `mentor-memory.tsx` (see §3 inventory). The guardian screen additionally offers a plain-text memory-summary export (`child/[profileId]/mentor-memory.tsx:250-282`), and account-level JSON export on the Privacy & data screen includes "semantic-memory content" per the draft privacy policy §9 (`docs/compliance/privacy-policy.html:64`).

**The gaps are concentrated in three places.** (1) The **child-facing layered explanation**: the child-readable privacy summary's current "learning memory" section describes the activity-summary memory (subjects, progress, notes), not the person-profiling memory the feature adds (interests, strengths, struggles, communication notes); a dedicated child-notice memory section exists as draft v0.1 but is deliberately **not inserted** until unlock, contains a placeholder for the guardian-role paragraph, and — like all of this copy — **has never been comprehension-tested with any young person** (`2026-07-30-child-notice-memory-section-draft.md:7,27,43`). (2) The **Privacy & data screen** (`apps/mobile/src/app/(app)/more/privacy.tsx`) contains no memory row or memory-consent control today; surfacing one there is planned as WI-2928 `[GAP: WI-2928 has no in-tree artifact in this working tree — referenced as planned work per tasking; remedy: land WI-2928 and cite the shipped surface]`. (3) The **consent prompt copy is thin at the decision point**: one sentence, with no statement of duration, deletion rights, or the no-advertising/no-training commitments the notice drafts make elsewhere (copy-inventory §1 row 1; verified against `en.json:4512-4518`).

## Child-facing explanation — assessment

**What exists.** Two layers of child-facing explanation exist in draft, plus live in-app copy:

1. The child-readable summary's "What 'learning memory' means" section (surface 2). It is well-pitched in register (short sentences, second person, concrete) but describes only the **activity-summary** memory — "subjects, progress, mastery results, notes, recaps, and short quotations" (:25). It does not explain the person-profiling dimension the memory feature adds: interests, strengths, struggles, communication notes, accommodation-relevant preferences — i.e. the exact categories the mentor-memory screen renders (`mentor-memory.tsx:535-760`). A child who read this section and then opened the memory screen would find categories the notice never mentioned.
2. The dedicated child-notice memory section, draft v0.1 (surface 3), written precisely to close that gap: it distinguishes the new memory from the existing one (:15), explains why (:17), what is and is not remembered (:19, :21), that it can be seen (:23) and turned off (:25). It is the right artifact, in the right voice, matched to the summary's reading level (:40). It is, however: (a) not inserted — correctly, since insertion before unlock would misdescribe the DPO-parked posture the package is meant to close out; (b) carrying an explicit placeholder for the guardian-role paragraph, blocked on the child-best-interests / guardian-visibility scope ruling (:27, :42); (c) silent on **correction and deletion** — it covers see and turn off but not "you can remove one thing" or "you can clear it all", both of which the app actually offers (surface 4); (d) untested with any young person (:43).

**What the in-app copy contributes.** The live memory screen is itself the strongest child-facing explanation in the estate — "What your mentor knows about you", per-category plain-language rows, and a clear-dialog that states the consequence of clearing ("removes everything the mentor has remembered about you and turns memory off until you enable it again", `en.json:781`). The 2026-07-30 copy inventory reached the same conclusion ("functionally, this is the strongest transparency surface in the app today", §1 row 2).

**Missing copy, concretely:**

- **Decision-point disclosure.** The consent prompt (surface 5) is where a child or guardian decides; it currently says one sentence about benefit and nothing about duration ("while your account is active"), the right to delete items or clear everything, or the no-ads/no-training commitments. The copy inventory already proposed aligning it with the child-notice draft (§1 row 1). This is the highest-value single copy change in this slice.
- **Correct/delete sentences in the child notice.** Add two sentences to the draft section: that individual remembered items can be removed, and everything can be cleared — mirroring functionality that already ships.
- **Duration statement in-app.** No in-app memory surface states how long memory is kept; only the (unpublished) policy §8 does. `[GAP: no retention statement on the memory screen or consent prompt — remedy: one sentence at the consent prompt and/or memory-screen status card, sourced from the retention-schedule slice of this package]`
- **Guardian-role paragraph.** Blocked on the guardian-visibility scope ruling — an input to this package, not producible within this slice.
- **Locale parity.** Any of the above lands as a DPO-ruled copy change across 7 locales; the WI-2919 audit sized the fully-in-scope key set at 129 keys per locale (§7 item 3) — new keys are additive but must follow the same 7-locale discipline (`docs/i18n.md` per repo rules).

## Proposed proportionate comprehension-testing protocol

> **PROPOSAL — for DPO review and approval before execution.** Nothing below has been run. Scope is deliberately limited to the memory disclosures, per the DPO's ruling that the full Art 35(9) programme is outside this closure set. The child-readable summary (:3) and the child-notice draft (:43) both already name comprehension testing as an unmet gate; this protocol is the proportionate instrument to meet it for the memory slice only.

**Materials under test (fixed set):**
1. The child-notice memory section (surface 3), as revised with the correct/delete sentences proposed above.
2. The consent-prompt copy (surface 5), as revised.
3. Static screenshots of the live mentor-memory screen (surface 4) — populated with fictitious sample data; no live accounts are used (the product has zero users pre-launch and no child's real data may be created for testing).

**Participants.** 8–12 young people aged 13–17 (the launch child population: age floor 13, `privacy-policy.html:22`; the app's age-bracket model places 13–17 in one 'adolescent' bracket, `packages/schemas/src/age.ts:5-8`, but for comprehension purposes the bracket is split): minimum 4 participants aged 13–14 and 4 aged 15–17. Recruitment outside the product (e.g. school/community contacts), with written parental consent and participant assent; no participant identifiers retained beyond age band and session date. English-language sessions first; see locale note below.

**Method.** Individual moderated sessions, 20–30 minutes, paper/screenshot based:
1. Participant reads the notice section and consent prompt unaided.
2. Comprehension questions — the four prompts already embedded in the child-notice draft (:29-34: what is different about this memory; where to see it; how to stop it; is it used for ads/selling) plus prompt 2 from the summary's existing prompt set (:60: what is the learning memory and why is it kept) plus two questions this slice adds: "If the mentor remembered something wrong about you, what could you do?" and "How long does MentoMate keep this memory?"
3. Task prompts on screenshots: point to where you would (a) see what the mentor remembers, (b) turn memory use off, (c) remove one remembered item, (d) clear everything.
4. Free-response: "Say in your own words what you just agreed to (or chose not to)."

**Pass criteria (per question/task, per age band):** at least 80% of participants in each band answer correctly or complete the task without moderator help. Any item below threshold → the copy (not the child) is treated as the failure: revise the wording, re-test the failed items with a fresh minimum of 4 participants in the affected band. Two consecutive failed rounds on the same item escalate to the DPO as a design question rather than a wording question.

**Documentation.** A dated results record under `docs/compliance/evidence/` (per-question tallies by age band, verbatim misunderstanding examples, copy revisions made, no personal data), referenced from this package. The record is the "proportionate testing … to demonstrate that the memory disclosures are understandable" evidence the DPO's ruling calls for, and supports GDPR Art 12(1)/Recital 58.

**Locale note (for DPO ruling).** The copy ships in 7 locales. Proposal: test English (the copy-authoring locale) in full; spot-check one translated locale with 3–4 participants (Polish suggested, as the current GTM focus market) after the English copy stabilises; defer the remainder with recorded rationale (translations are of tested source copy under the repo's i18n discipline). Alternative — English only, with the locale question deferred to the full Art 35(9) programme — is also defensible; recommendation is the spot-check variant.
