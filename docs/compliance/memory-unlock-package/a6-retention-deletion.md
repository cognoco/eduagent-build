## Current position

The deletion *mechanisms* for the categories in scope are implemented, code-verified, and — for the raw-content purge — confirmed running in production. The repository holds two prior Action 6 artifacts: a working-notes inventory with full `file:line` citations (`docs/compliance/evidence/2026-07-26-retention-schedule-draft.md`) and the six-column schedule that supersedes it for DPO presentation (`docs/compliance/evidence/2026-07-30-retention-schedule.md`). Raw conversation turns (`session_events`) are hard-deleted on a 30-day policy clock after the session summary is generated, in the same transaction that rewrites the session's Voyage-derived embedding from summary-only text (`2026-07-26-retention-schedule-draft.md` §3.2); the production gate `RETENTION_PURGE_ENABLED` defaults to `false` in code (`apps/api/src/config.ts:122`, read this pass) and was verified `true` in the production Doppler config on 2026-07-26 (draft §3.2); a completed production run of the purge cron is evidenced in `docs/compliance/2026-07-24-wi-1194-production-transcript-purge-evidence.md`. Whole-account and person-scoped erasure run through durable Inngest pipelines that cascade the database, re-home consent evidence into a deliberately surviving retain-tier, and then erase the external Clerk login and dispatch subscription-store teardown (`apps/api/src/inngest/functions/account-deletion.ts`, read in full this pass).

Retention *periods*, by contrast, are only partly settled. Periods that exist in code are cited below (30-day transcript purge; 30/37/90-day TTL crons on operational tables; 24-hour KV cache). Three period classes are **not set anywhere**: (i) the `retention_period` columns on the three retain-tier tables (`consent_receipt`, `deletion_audit`, `financial_record`) are NULL/unset — an explicitly counsel-owned seam, not an accident (`2026-07-26-retention-schedule-draft.md` §2 row 7b, gap G-2); (ii) the Neon backup/PITR window is a console-level plan setting that the repository deliberately refuses to hardcode (`docs/runbooks/neon-pitr-identity-recovery.md` §2, read this pass); (iii) no provider-held-copy retention window is vendor-confirmed for any LLM/embedding provider — the DPA/evidence packs under Actions 7–9 are still in flight as of 2026-08-07 (`2026-07-26-action-register-tracker.md` rows 7–9).

Directly relevant to this package: the `MEMORY_FACTS_*` config flags all default `false` (`apps/api/src/config.ts:151–153`, read this pass), but — as the A3 and A13 sections establish in detail — these are **storage-generation selectors, not a feature gate**: with the flags off, memory reads fall back to the legacy JSONB profile columns rather than returning empty. The interim condition is held by the per-profile fail-closed consent defaults plus the pre-launch zero-user state, dispositioned provisionally by the operator on 2026-08-05 pending DPO ratification (OPQ-169); this section defers to A3 §3 for that account. The `memory_facts` store (the "derived profile" substrate this package would unlock) already carries `ON DELETE CASCADE` to `person.id` (`packages/database/src/schema/memory-facts.ts:24`, read this pass), so the erasure design covers it before the feature is enabled. Deletion-propagation test evidence exists at the automated-test level (cited per row below) but the 15-item end-to-end propagation drill proposed in the July 26 draft §6 has not been executed (`2026-07-30-retention-schedule.md` §2).

## Deletion design narrative

**Whole-account erasure (owner-initiated).** `POST /account/delete` schedules deletion; the durable Inngest function `scheduled-account-deletion` (`apps/api/src/inngest/functions/account-deletion.ts`, read in full this pass) sleeps a 7-day grace period, re-checks cancellation, captures a complete external-erasure snapshot (person ids, Clerk user ids, login emails, store-subscription targets — lines 177–196), then runs `executeDeletionV2` in one Postgres transaction. Per the mechanism inventory (`2026-07-26-retention-schedule-draft.md` §3.1, which carries the `deletion-v2.ts` file:line cites): the transaction tears down guardianship/supportership edges, hard-deletes subscription rows, re-homes live `consent_grant` rows into `consent_receipt`, writes `financial_record` and `deletion_audit`, hard-deletes the `person` row (cascading ~55 tables including sessions, summaries, embeddings, memory facts, learning profiles), deletes the organization, and erases any matching `byok_waitlist` row. The transaction commit is the documented irreversibility boundary (`docs/runbooks/deletion-irreversible-boundary.md`, referenced by the draft; not opened this pass). TOCTOU cancellation races and snapshot drift are handled with atomic guards and a bounded single re-snapshot (`account-deletion.ts:199–244`).

**External legs.** After the DB commit, the pipeline erases the Clerk login identity with a reservation fence that blocks same-Clerk re-bootstrap during erasure (`account-deletion.ts:277–325`), and dispatches the subscription-store teardown event (`account-deletion.ts:252–266`). Neither leg can silently fail: throws retry, and exhausted retries escalate.

**Dead-letter safeguards (WI-2994 sanctioned exception).** Both terminal-failure handlers emit machine-queryable dead-letter events — `app/account.deletion_teardown.failed` (`account-deletion.ts:50–99`; awaited `step.sendEvent` at lines 90–96 with a deterministic event id) and `app/billing.subscription_store_teardown.failed` (`apps/api/src/inngest/functions/billing-subscription-store-teardown.ts:27,64`, read at those lines this pass) — alongside a Sentry exception tagged for "how many erasures terminally failed?" queries (`account-deletion.ts:65–81`). These two functions intentionally use awaited `step.sendEvent` rather than the repo-standard `safeSend()` because losing the dead-letter would be worse than the coupling (sanctioned exception, `AGENTS.md` § Known Exceptions, WI-2994). Manual operator remediation of the half-completed external erasure remains required; chat/pager routing of the alert is parked under WI-1916 (`2026-07-26-retention-schedule-draft.md` G-8).

**Person-scoped erasure (consent withdrawal).** Two pipelines delete a single person without touching siblings: the guardian-initiated path (`consent-revocation.ts`: 6-day sleep → warning → 1-day sleep → re-check → age-gated branch) and the email-consenting-parent bearer-token path (`consent-email-revocation.ts`), both terminating in `deletePersonIfConsentWithdrawnV2` FK-cascade deletion (`2026-07-26-retention-schedule-draft.md` §3.3; threat model for the bearer-token trigger: `docs/compliance/2026-07-17-consent-withdrawal-bearer-token-threat-posture.md`).

**Archive-first, precisely scoped.** Genuine server-side archive-first behavior exists on the COPPA-age consent branch: `archivePersonOnRevocationV2` archives the child's person, and `archive-cleanup.ts` deletes it 30 days later only if consent was not restored (`ARCHIVE_RETENTION_MS`; draft §3.4). By contrast, the "archive-first subject delete" from the PR #787 era is **client-side confirmation UX only** — the server's `deleteSubject` is a direct hard `DELETE` with FK cascade (draft §3.6, citing `docs/flows/student-flow-access-inventory.md:73`: "archive-first is client-only (server gap)"). This package must not represent subject deletion as a server-side soft delete.

**Retention purge as designed abstraction, not data loss.** The 30-day transcript purge deletes raw turns only after the pedagogical value is abstracted into a summary, regenerates the session embedding from summary-only text in the same transaction, and treats deferral (missing summary, embedding-provider failure) as an operational retention incident with day-37 escalation rather than a silent skip (`2026-07-30-retention-schedule.md` §1 row 1).

**Backup interaction.** Because a Neon PITR restore restores only Postgres — never Clerk or the stores — and can resurrect both a deleted person and the deletion-evidence rows, the deletion pipeline writes an out-of-band completion record (structured log + Sentry, `account-deletion.ts:333–374`, WI-2390) and the PITR runbook mandates a manual capture→freeze→restore→replay procedure preserving deletion supremacy (`docs/runbooks/neon-pitr-identity-recovery.md` §5). The procedure is documented but has not been drill-proven (see Gap 3).

## Gaps and proposed remediation

1. **Retain-tier retention periods unset (G-2 — blocking for A6 closure).** `consent_receipt` / `deletion_audit` / `financial_record` carry `retention_period` columns that are NULL/unset; counsel owns the values. The 07-30 schedule proposes 6y / 3–5y as drafts only (`2026-07-30-retention-schedule.md` §1 row 7b). **Remedy:** obtain counsel/DPO ruling on the three values; write them into the columns and the schedule. Tracking: draft gap G-2; DPIA §9 item 7 per the draft.
2. **Verbatim learner quotes outlive the 30-day purge (G-1 / A24-b).** `learnerQuote` copies inside `learning_sessions.metadata` survive indefinitely while the child-facing notice describes 30-day chat deletion (`ropa.md` line 80; `2026-07-30-retention-schedule.md` §1 row 3). **Remedy:** DPO/product ruling — either add an age-out or align notice wording. Tracking: A24-b (open, post-launch tightening per `ropa.md`).
3. **Backup window undocumented and PITR replay drill unexecuted (G-9).** No Neon PITR window or snapshot cadence is recorded in the repo (deliberate, `neon-pitr-identity-recovery.md` §2); the deletion-supremacy replay procedure is manual and its 3-case drill has never been run (`2026-07-30-retention-schedule.md` §1 row 12). **Remedy:** (a) read the Neon console once and file a dated record of the window per branch; (b) execute the §6 drill on a non-production branch and file results. Tracking: WI-2390 (deletion recovery), WI-2056/WI-2057 (forward-repair primitives).
4. **No vendor-confirmed provider retention window (Actions 7–9 dependency).** DPAs/ZDR/opt-out evidence is filed (`docs/compliance/evidence/providers/`), but no provider's own retention period is confirmed in a dated, org-identifying reply; all five requests are pending with tripwires 2026-08-11/13/15; OpenAI config evidence is blocked on the P2 account migration (`2026-07-26-action-register-tracker.md` rows 7–9, P2). Voyage zero-retention activation state is ambiguous between `providers/README.md` line 38 (pending, 2026-07-24) and the 2026-07-30 opt-out screenshot. **Remedy:** close Actions 7–9 before representing the provider row as complete; confirm and file the Voyage zero-retention state. This slice should be sent flagged as dependent on Actions 7–9 per the DPO's own unlock condition ("any provider … used for memory must first satisfy A7–A10").
5. **Deletion-propagation test evidence is partial.** Real automated evidence exists — the DB cascade chain including embeddings (`transcript-purge.integration.test.ts:157–209`), the purge transaction (`transcript-purge.test.ts:96–276`), the erasure pipeline's snapshot/fencing/teardown behavior (`deletion-v2.integration.test.ts`, 27 tests), and one recorded production purge run (WI-1194 evidence doc) — but the 15-item end-to-end propagation plan (retain-tier survival assertion, export/delete parity, `email_suppressions` negative check, KV invalidation, dead-letter drill, PITR drill, provider-copy verification) is unexecuted (`2026-07-30-retention-schedule.md` §2). **Remedy:** raise the proposed WI, execute the plan, attach run output to this package. Additionally add explicit assertions that `memory_facts` and `learning_profiles` rows vanish on person delete (currently schema-declared cascade only).
6. **No dormancy rule bounds "life of person" (G-3).** Derived profiles, summaries, and memory facts persist for the account's life with no dormant-account sweep in code (zero-match grep recorded 2026-07-26; `2026-07-30-retention-schedule.md` §1 row 11). For a memory feature marketed as persistent, "until deletion" may be defensible, but it must be a recorded decision, not an omission. **Remedy:** DPO/product ruling (the 07-30 schedule proposes a 24-month notify→grace→delete pattern as a draft); build if ruled. Tracking: none found — needs a new WI.
7. **Platform log/queue retention unconfirmed (adjacent).** Sentry project retention, Inngest event-payload retention, and Cloudflare Workers log retention have no confirmed values in the repo (`2026-07-26-retention-schedule-draft.md` §§4.4–4.5); `email_suppressions` has no purge path at all (draft G-4). **Remedy:** one dashboard-reading pass with dated screenshots; new WI for an `email_suppressions` age-out.
